## Saved-build write boundary

`vt_guard_saved_build_write()` now enforces the customer-side state machine at the database boundary.

For normal authenticated customers:

- a new build must start in `saved`;
- quote linkage fields cannot be supplied by the customer;
- an editable build can remain `saved` and be updated;
- `saved → quote_requested` is allowed only for a complete build with no hard compatibility conflict;
- an integrated-graphics build can omit a discrete GPU only when `serialized.gpuOptional` is true;
- quote request timestamps are generated by the server;
- after a quote request the customer cannot rewrite the build or promote it to another status;
- `quote_id` and `quoted_at` are admin/server managed.

The existing RLS owner boundary remains in place; the trigger adds field/state protection that RLS alone could not express.

## Quote-request RPC

The live Builder now uses:

`customer_request_build_quote(p_build_id)`

The browser no longer writes `status='quote_requested'` directly. The RPC changes only the authenticated user's own saved build and the trigger independently validates the transition.

## Atomic admin conversion

`admin-builds.js` now uses:

`admin_quote_saved_build(p_build_id, p_valid_until)`

The server performs the following in one database transaction:

1. locks and validates the `quote_requested` saved build;
2. creates the draft system-build quote;
3. creates quote items from the saved Builder items;
4. preserves Builder product/source metadata;
5. links the quote source to the saved build;
6. updates the saved build to `quoted` with `quote_id` and `quoted_at`.

This replaces the previous browser sequence of `admin_create_quote` → `admin_link_quote_source` → direct `saved_builds.update()`, which could leave partial state if a later step failed.

The admin UI now also calls out how many saved estimates have stale, unknown or missing source timestamps so the operator knows pricing must be refreshed before sending the formal quotation.

## Price and supplier provenance

The retired account integration selected the first positive supplier price and could write `new Date().toISOString()` when no source timestamp existed. That could make stale prototype data appear newly checked.

The clean Builder account service now uses the same `getBestOffer()` selector as the Builder UI and stores:

- supplier name/source;
- supplier SKU;
- stock status;
- the actual normalized `lastChecked`, or NULL;
- offer freshness (`fresh`, `aging`, `stale`, `unknown`);
- stale flag;
- pricing basis.

Regression coverage verifies that a fresh eligible offer is preferred over a cheaper stale offer.

`admin_create_quote` was corrected so an absent `price_checked_at` stays NULL. This is a truthfulness fix: callers that genuinely checked a price can still send a timestamp; callers without source evidence no longer receive a fabricated one.

## Rollback

Repository rollback target: `bbf3001d8b0a206ca95401d18e3d507fef040b65`.

The database migration is intentionally backwards compatible with the Step 3.2 frontend: the old customer transition `saved → quote_requested` remains valid when the build is complete, and authenticated VoltTech admins remain permitted to perform the old admin update flow. Therefore a frontend rollback does not require an emergency database rollback.

Do not remove the database guard merely to roll back presentation/client code; doing so would weaken the saved-build boundary.
